## Abstract

This ERC standardizes a single smart-account method:

```solidity
function executeWithSig(bytes32 mode, bytes calldata executionData, uint256 nonce, uint256 deadline, bytes calldata signature)
    external payable returns (bytes[] memory results);
```

Anyone (a low-trust *relayer*) may submit a signature-authorized execution and pay the gas; the account
validates the signature over an [EIP-712](./eip-712.md) digest and runs the calls, enforcing whatever policy
it likes during execution — including stateful, cumulative limits backed by storage. The execution
payload reuses the [ERC-7579](./eip-7579.md) `mode` / `executionData` encoding (single or batch). A
single-use `nonce` provides replay protection, and a `deadline` bounds the signed payload's validity in time.

Together with an optional off-chain payment-negotiation handshake (Section *Payment Profile*), this forms a
stateful, smart-account-native payment rail: a complement to stateless authorization schemes such as
EIP-3009 / x402, which cannot enforce a running budget on-chain.

## Motivation

Autonomous agents and automated payers need budgets they cannot exceed, enforced trustlessly.

- **Stateless authorization (EIP-3009, x402) cannot bound cumulative spend.** `transferWithAuthorization` is
  a one-shot, independent authorization. There is no on-chain notion of "this payer has spent 42 of its 50
  USDC this period." To impose a running cap, the limit must live in a trusted off-chain facilitator or
  server — exactly the custodial trust this standard exists to remove. (x402's *facilitator* is itself a
  relayer that submits the authorization and pays gas; the trust difference is not gas, it is *where the
  policy lives*.)

This ERC takes the minimal path: a plain account method where (a) a low-trust relayer pays gas and can
only submit what was already signed and policy-gated, (b) policy — including stateful budgets — is enforced
on-chain during the call, and (c) the account needs no native balance for gas (the relayer pays it). It is
deliberately signature-scheme-agnostic, and it interoperates with ERC-7579 execution tooling and ERC-1271
signature validation.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", and "MAY" are to be interpreted as described in RFC 2119.

### Interface

A conforming account MUST implement:

```solidity
interface IERC1608 {
    /// @notice Emitted on a successful execution (it reverts otherwise, so the event marks success).
    event Executed(uint256 indexed nonce);

    /// @notice Validate `signature` over the execution digest, then run the ERC-7579 execution.
    /// @param mode          The ERC-7579 execution mode (selects single vs batch).
    /// @param executionData The ERC-7579-encoded call(s).
    /// @param nonce         A single-use, caller-chosen nonce (order-independent).
    /// @param deadline      Unix timestamp after which the signed payload is no longer valid.
    /// @param signature     An account-defined authorization over the EIP-712 execution digest.
    /// @return results       Each call's return data, in order.
    function executeWithSig(bytes32 mode, bytes calldata executionData, uint256 nonce, uint256 deadline, bytes calldata signature)
        external
        payable
        returns (bytes[] memory results);
}
```

A conforming account MUST return `true` from [ERC-165](./eip-165.md) `supportsInterface` for
`type(IERC1608).interfaceId`.

### Execution payload

`mode` and `executionData` MUST follow ERC-7579:

- **Single** (`getCallType(mode) == 0x00`): `executionData = abi.encodePacked(address target, uint256 value, bytes data)`.
- **Batch**  (`getCallType(mode) == 0x01`): `executionData = abi.encode(Execution[])` where `Execution { address target; uint256 value; bytes callData; }`.

The account MUST execute the calls atomically: if any call reverts, or the account's policy rejects any call,
the **entire** `executeWithSig` MUST revert. A `target` of `address(0)` resolves to the account itself.

### Digest

The signature MUST be over the EIP-712 typed-data digest of:

```
Execute(bytes32 mode,bytes32 executionDataHash,uint256 nonce,uint256 deadline)
```

with `executionDataHash = keccak256(executionData)`, under the account's EIP-712 domain (which MUST bind
`chainId` and the account address `verifyingContract`). The account MAY name the type domain as it wishes;
the struct fields and order are normative.

The digest is the **interoperability and replay surface** — it is mandated (not implementation-defined) so
that any relayer or SDK can construct the exact message to sign regardless of the account's signature scheme,
and so the replay-protection fields are enforced uniformly. The **signature scheme** (how the digest is
authorized) is the orthogonal trust surface and is left to the account (see *Signature validation*).

### Deadline

The account MUST revert if `block.timestamp > deadline`. The check MUST happen before the calls run, and
`deadline` MUST be bound in the digest above so a relayer cannot alter the validity window the signer agreed
to. A signer MAY pass `type(uint256).max` for a payload that never expires.

### Nonce

`nonce` MUST be single-use and MAY be chosen in any order (e.g. a random 256-bit value), tracked as
`mapping(uint256 => bool)`. The account MUST mark the nonce used **before** executing the calls
(checks-effects-interactions). Because a reverting execution rolls back that write, a failed execution leaves
its nonce **reusable** (retryable) — see *Security Considerations*.

### Signature validation (account-defined)

This ERC does **not** mandate a signature scheme. The account decides how to authorize the digest — ECDSA,
WebAuthn/passkey, multisig, a modal scheme that selects an owner set vs a scoped session key, etc. Accounts
SHOULD reuse ERC-1271 validators where applicable. Whatever the scheme, the authorization MUST be over the
digest above.

### Stateful policy

A conforming account MAY enforce arbitrary policy while executing, including stateful policy that reads and
writes storage (e.g. a rolling daily cap, a cumulative budget, usage counters). This is what distinguishes
signed execution from stateless authorization: the limit is enforced by the contract, not by a trusted
off-chain party.

The *enforcement mechanism* is intentionally account-defined and is NOT part of this ERC's interoperable
surface — two conforming accounts MAY implement budgets with entirely different internal logic. An account
that exposes a stateful budget to off-chain payers SHOULD make the relevant state observable (an introspection
view and/or an event) so a payer can predict whether a payload will pass before submitting it.

### Policy hook (optional)

An account MAY bracket the execution with a pre/post policy hook that runs once before and once after the
call set. This enables *cumulative* invariants — e.g. a spend cap measured by the account's net balance delta
— that a per-call check cannot express:

```solidity
interface IExecutionPolicy {
    /// @notice Snapshot pre-execution state; called once before the calls run.
    function preCheck(address account) external;

    /// @notice Assert the post-execution invariant over the whole executed payload; revert on violation.
    function postCheck(address account, bytes32 mode, bytes calldata executionData) external;
}
```

`postCheck` receives the entire executed `mode` / `executionData`, so the invariant is global over the batch
(it can itemize every call's effect) rather than a per-call attachment. Both hooks run inside the same atomic
frame as the calls, so a `postCheck` revert unwinds the whole execution and any cumulative state it wrote
persists only on success.

### Payment Profile (optional, off-chain)

A stateful payment rail layers an off-chain negotiation over the on-chain method, analogous to x402's HTTP
402 flow:

1. The resource server responds with a payment requirement: token, amount, `payTo`, network, and a
   server-chosen reference id.
2. The payer's agent builds an `executeWithSig` payload that performs the payment (e.g. an ERC-20 transfer to
   `payTo`), signs the digest, and hands it to a relayer (or directly to the server's facilitator).
3. The relayer submits it; the payer account's **bound policy enforces the budget on-chain**.
4. The server treats the payment as **pending until confirmed** (the `Executed` event + the on-chain
   transfer / a receipt), and grants the resource only on confirmation.

## Rationale

- **Reuse ERC-7579 `mode`/`executionData`** so existing executor tooling (incl. ERC-7821) can encode calls.
  Only the execution *encoding* is borrowed — this ERC does NOT require an account to be an ERC-7579 modular
  account, to install modules, or to use the ERC-4337 EntryPoint.
- **Why not just a 7579 validator / session-key executor?** Those standardize *per-call, stateless*
  authorization. This ERC's contribution is two-fold: (a) one standardized `executeWithSig` entrypoint plus a
  mandated EIP-712 execution digest, so any relayer or SDK has a single interoperable signing surface
  independent of the account's signature scheme; and (b) elevating *stateful, on-chain* policy (cumulative
  budgets) to a first-class part of that surface, which stateless per-call authorization structurally cannot
  express.
- **Signature-scheme-agnostic** so the method composes with ERC-1271, passkeys, and modal validation rather
  than fixing a single owner model.
- **Single-use nonce, CEI burn with revert-rollback** makes execution replay-safe yet retryable, so
  front-running degrades to a retry rather than a permanent block (see below).
- **Low-trust relayer** — it can only submit already-signed, already-policy-gated payloads, and it pays the
  gas, so the account needs no native balance to transact.
- **On-chain stateful budgets** give trustless cumulative limits, which stateless authorization (EIP-3009)
  structurally cannot.

## Backwards Compatibility

This ERC adds a method; it does not change existing ones. It is complementary to EIP-3009 / x402 (an account
MAY accept both).

## Security Considerations

- **Front-running / liveness.** Two cases. (a) Front-running the *submission*: the payload is
  signature-bound, so it executes exactly once and cannot be redirected; an attacker who lands it first only
  causes the honest relayer to waste gas on a now-duplicate. In practice the signed payload is delivered
  privately to a relayer, not broadcast, so there is nothing to grab. (b) Front-running to force a *revert*
  (e.g. exhausting a rolling budget, or slippage): because the nonce is rolled back on revert, the execution
  is **retryable**; nothing is stolen. Payees MUST grant resources only on confirmation, so a reverted
  payment is simply "declined / retry" — normal payment semantics. The budget *race* is the inherent cost of
  statefulness (a finite shared resource serialized by the chain) and degrades to a retry.
- **Relayer trust.** Minimal: a relayer cannot forge a signature or exceed policy. Censorship is mitigated
  because relaying is permissionless (the user can self-submit the same payload).
- **Replay.** The EIP-712 domain MUST bind `chainId` and the account, preventing cross-chain / cross-account
  replay; the single-use nonce prevents same-account replay; and the `deadline` bounds a signed payload's
  validity in time, so a payload that is never relayed (or whose nonce is rolled back by a revert) cannot be
  held and submitted arbitrarily far in the future.
- **Signature malleability.** Deferred to the account's validator; passkey (P256) implementations MUST
  enforce low-s.

## Reference Implementation

DAIMON implements this ERC: `Daimon.executeWithSig` (the dispatch + nonce + digest), `ExecLib`
(ERC-7579 decode + per-call policy enforcement + execution + the outcome pre/post hook), `OmniSigil` (the
per-call action sigil — recipient locks, allowlists via `checkAction`/`check1271`), and `SpendSigil` (the
per-execution outcome sigil — the stateful rolling spend cap). See `contracts/`.
